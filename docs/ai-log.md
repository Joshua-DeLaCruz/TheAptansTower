## 2026-10-28 – M1 step 2: player input reader
**Task:** Make one `PlayerInputReader` component that reads all player input (Move, Jump, Dodge, Attack, Throw) with the new Input System and passes it to other scripts through properties and C# events.
**What the agents did:** First the coordinator repaired the git history: local main had no parent and did not connect to GitHub's "Initial check-in", so it was put on top of that commit, the URP settings were restored from it, and with my OK three leftover folders inside `.git` were deleted (an old project copy, a 177 MB Unity cache and a nested old repository). Step 1 was then committed (ed4946f). When I tested step 1, the scene, sprite and layers were missing from this folder, probably because I ran the builder in my backup copy, so I was asked to re-run it here. Lesson: always check which project folder Unity has open before testing. The unity-gameplay agent wrote `Assets/_Project/Scripts/Player/PlayerInputReader.cs` with serialized `InputAction` fields, default keyboard and gamepad bindings in `Reset()` (filled in by `Awake` if empty), polled values (`Move`, `MoveX`, `JumpHeld`), events for one-off presses, subscribe/unsubscribe in OnEnable/OnDisable, Dispose in OnDestroy, a Log Input toggle, and Digital mode for keyboard diagonals. It also made the scene builder add the reader to the Player. The code-reviewer checked it, and the learning-coach wrote the explanation and this entry.

Five small fixes, all applied: removed the Play-mode Reset branch, added Dispose in OnDestroy, fixed a comment, documented that JumpReleased does not fire if the reader is disabled while Jump is held (so jump code should poll JumpHeld), and documented that the defaults come back if all bindings of an action are removed in the Inspector. ## 2026-10-28 – M1 step 3: player movement, jump and camera follow
**Task:** Make the player run and jump (with coyote time, a jump buffer and variable jump height) and make the camera follow the player inside the level edges.
**What the agents did:** I tested steps 1 and 2 in Unity and both worked. An earlier worry was a misunderstanding: I simply had not run the builder yet. Step 2 was committed (a0bcdeb). The unity-gameplay agent wrote `Assets/_Project/Scripts/Player/PlayerMovement.cs` and `Assets/_Project/Scripts/Arena/CameraFollow.cs`. PlayerMovement has run speed with separate ground and air acceleration, a narrow overlap-box ground check that only counts when not rising, a jump defined by height (launch speed sqrt(2·g·h)), a jump cut when Jump is released, coyote time and a jump buffer stored as timestamps, a fall-gravity multiplier, a max fall speed, flipping only the `Visual` child, and `IsGrounded`, `Jumped`/`Landed` and `SetControlLocked` for the dodge later. CameraFollow uses SmoothDamp with a dead zone and is clamped to the level edges. The scene builder now adds a zero-friction PhysicsMaterial2D, so the player can't stick to walls. The code-reviewer checked it, and the learning-coach wrote the explanation and this entry.
**Review findings:** No must-fixes. The most useful catch: the reviewer simulated the 50 Hz physics steps and found the real jump peak was about 4.04 instead of 4.2, because the steps lose about half a gravity step of height. That meant platform D (3.75 up) was only cleared by about 9 art pixels. Fix: add 0.5·g·dt to the launch speed so `jumpHeight` is the real peak, and raise it to 4.4. Other fixes, all applied: a minimum jump time before the jump cut (so a buffered tap isn't cut in its first step), fall gravity only when airborne, gravity restored in OnDisable, no false Landed event at scene start, the camera reads PixelPerfectCamera's size, friction combine set to Minimum, and comment fixes. Not yet tested in Unity.
