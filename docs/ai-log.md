## 2026-10-28 – M1 step 3 follow-up: camera vertical follow
**Task:** Change the camera's vertical follow so it ignores small jumps and rises less the higher I climb, with an Inspector setting for how strong that is, so the ground stays in view on high platforms.
**What the agents did:** I tested step 3 in Unity and liked it, so it was committed (604facb). On the gold platform I could no longer see the ground, so I asked for this change and asked for the approach to be explained first. I approved it. The approach: the camera follows a "ground height" (my Y the last time I was grounded) instead of my live height, so jumps don't move it. Drops below that height are followed fully, and a screen edge margin always keeps me on screen. Above the starting height the camera only rises `verticalFollowStrength` (0.35) of each climb, so on platform D it rises about 2.2 units instead of about 6. X and Y are smoothed separately. The unity-gameplay agent changed `Assets/_Project/Scripts/Arena/CameraFollow.cs` (new Inspector values: Vertical Follow Strength, Vertical Smooth Time, Screen Edge Margin). The code-reviewer checked it, and the learning-coach wrote the explanation and this entry. Note on how the agents worked: this time they checked their work outside Unity. The unity-gameplay agent compiled the script against the Unity DLLs and simulated the camera frame by frame in Python, and the code-reviewer ran its own simulation that included Unity's SmoothDamp. This is new compared to earlier steps. It is not a replacement for testing in the Editor.
**Review findings:** One real bug: a buffered jump can land and jump again within the same physics step, so the camera never saw `IsGrounded = true` and did not rise when chaining jumps from A to B. Fix: the camera now also listens to the `Landed` event. Smaller fixes, all applied: `[Min]` attributes on the tuning values, `smoothTime` renamed to `horizontalSmoothTime` with `FormerlySerializedAs` so the old Inspector value is kept, and a warning when no PlayerMovement is found. The reviewer also confirmed that the `deltaTime == 0` guard is needed, because SmoothDamp can return NaN while the game is paused. Left for later: reset the base height on respawn or floor change, and maybe faster vertical smoothing when falling (I will judge that in the Editor). Not yet tested in Unity.

## 2026-10-28 – M1 step 4: player dodge
**Task:** Give the player a short, fast dodge with i-frames (a window in which hits are ignored) that works on the ground and once per jump in the air, and that raises events for the M3 tracker.
**What the agents did:** I tested the camera follow-up in Unity and liked it, so it was committed (b4a557e). The coordinator chose the dodge defaults and told me what they were: ground and air dodge (one air dodge per jump), i-frames for the first 0.2 s of the 0.25 s dodge so the end can still be hit (souls-like), a placeholder tint while invulnerable, and `DodgeStarted`/`DodgeEnded` events for the tracker. The unity-gameplay agent wrote `Assets/_Project/Scripts/Player/PlayerDodge.cs`. The press is buffered and handled in FixedUpdate. The dodge is tuned by distance and duration (speed = distance / duration, counted in physics steps, with a partial last step so the distance is exact). During the dodge it locks PlayerMovement, sets gravity to 0 and keeps the velocity flat. At the end it hands back run speed if I hold the direction, and the cooldown starts from that moment. It has `IsInvulnerable` for Health to check later, and it runs before movement in each physics step (`[DefaultExecutionOrder(-10)]`). Small changes elsewhere: `PlayerMovement` got `RunSpeed` and `SetFacing`, and restores its own gravity on unlock. `PlayerInputReader` now runs first (`[DefaultExecutionOrder(-50)]`). The scene builder adds PlayerDodge to the Player and links the Visual's SpriteRenderer for the tint. The agent compiled the code against the Unity DLLs, and a simulation confirmed exactly 3.5 units of travel and 0.2 s of i-frames. The code-reviewer checked it, and the learning-coach wrote the explanation and this entry.
**Review findings:** One must-fix, a real but intermittent bug: `PlayerInputReader` and `PlayerMovement` both read in Update, and Unity doesn't promise which Update runs first. When Left and Dodge were pressed in the same frame, facing could update one frame late. The dodge then locked it, so the player faced the wrong way, and later attacks would too. Fix: input runs first (order -50), and the dodge also sets facing itself. Smaller fixes, all applied: the dodge won't take over a lock owned by another system, PlayerMovement always restores its own gravity on unlock, the tint restores a colour captured once in Awake, old presses expire during a dodge, the i-frame window is clamped inside the dodge, and a new `DodgePressTime` property lets the M3 tracker measure reaction time from the press instead of from the physics step. Not yet tested in Unity. Next is step 5 (Health/IDamageable), which I write myself from outlines.

## 2026-10-28 – M1 step 4 follow-up: ground-only dodge, jump i-frames and jump-cancel

During a dodge it checks the same `HasBufferedJump`/`CanJump` that `PlayerMovement.TryJump` uses, and if a jump is ready it ends itself, so PlayerMovement jumps in the same physics step. This relies on execution order: Input -50, Invulnerability -20, Dodge -10, Movement 0. ## 2026-10-28 – M1 step 4 follow-up: dodge-jump carry
**Task:** Make a jump that cancels the dodge keep going in the dodge's direction (even with no direction held) with part of the dodge's speed, fading during the jump, and find out how far the longest dodge-jump goes compared to a normal running jump.
**What the agents did:** I tested the ground-only dodge, the jump safe window and the jump-cancel in Unity, and everything worked. I then asked for this change, with the kept speed as an Inspector slider, Jump Cancel Speed Keep (0 = normal jump, 1 = full dodge speed, default 0.3). The unity-gameplay agent changed `PlayerDodge.cs` and `PlayerMovement.cs`. When a jump ends the dodge, the dodge "arms" a carry with `StartJumpCarry`, and PlayerMovement turns it on at take-off in `TryJump`. A carry that no jump uses in that physics step is dropped, so a normal jump never carries. While the carry is on, no input counts as holding the dodge direction, and a boost on top of run speed fades out linearly over Jump Cancel Boost Fade (0.35 s). The carry ends on landing, on steering back, or when movement is locked or disabled. `GAME_BRIEF.md` was updated with the decision. The answer to my question comes from a simulation that the code-reviewer confirmed: at Keep 1 the dodge-jump lands about 1.1 units further than a normal running jump (held jump 9.1 vs 8.0 units, +14%; tap 5.9 vs 4.8 units, +23%). At the default 0.3 it is only about +0.3 units. This matches the rule of thumb "extra distance ≈ ½ × extra speed × fade time". The code-reviewer checked it, and the learning-coach wrote the explanation and this entry.
**Review findings:** One must-fix: if I held the opposite direction at the cancel ("dodge through the boss, then jump back", a core souls move), the jump was still launched forward at dodge speed first and lost about 2 units. Fix: holding the opposite direction at take-off skips the carry, so it is a normal jump back. Take-off and the per-step steer-back check now use one shared helper (`IsSteeringAgainstCarry`), so the two rules can't drift apart. Other fixes, all applied: PlayerMovement now owns the carry speed, instead of it being set in two scripts; a "wall" rule was removed because it also ended the carry on thin platform edges; `TryGetCarryTarget` was renamed to `StepCarry`, because it changes state; a jump on the dodge's last step now carries too, so pressing one step later doesn't suddenly change the jump; and tooltip fixes. Not yet tested in Unity. Everything since b4a557e is still uncommitted, and I will test before the commit.
